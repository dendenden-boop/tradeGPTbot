# Зависимости PHASE 2

Срез: **2026-09-07**. Выбран Prisma ORM **7.10.0**; точные версии прочитаны из установленных manifests и сверены с официальными npm metadata. Этот документ фиксирует выбор и ограничения зависимостей, но не подменяет отчёт о выполненных проверках PHASE 2. Полный граф и integrity-хэши находятся в [pnpm-lock.yaml](../../pnpm-lock.yaml).

Это не размер runtime bundle, всего транзитивного графа, Docker-образа или потребление памяти. У `@prisma/client` в поставку входят варианты runtime/compiler для разных сред. Prisma CLI со Studio и вспомогательными зависимостями должен оставаться вне production deploy приложения.

Релиз 7.10.0 опубликован **25 августа 2026 года**, поэтому старше установленного порога `minimumReleaseAge: 1440`. npm metadata клиента и адаптера дают время публикации 12:54:34 и 12:40:21 UTC соответственно. При проверке registry тег `prisma@latest` указывал на **8.0.0-rc.13**, тогда как стабильные клиент и адаптер — на 7.10.0. Установка по `latest`, `dlx` без версии или смешивание CLI/client разных веток здесь не используются. Официальный [релиз Prisma ORM 7.10.0](https://github.com/prisma/orm/releases/tag/7.10.0) подтверждает эту стабильную ветку; дополнительный пакет совместимости `@prisma/prisma7` для одновременного использования Prisma 8 проекту не нужен.

CLI и client объявляют Node.js `^20.19 || ^22.12 || >=24.0` и TypeScript `>=5.4.0`; Node **24.20.0** и TypeScript **6.0.3** удовлетворяют этим диапазонам. Адаптер требует `pg ^8.16.3`, что допускает закреплённый **8.23.0**. Отдельного ограничения на pnpm в этих manifests нет; проект сохраняет **pnpm 11.25.0**, строгую проверку peers и engines. Prisma указывает поддержку Active/Maintenance LTS Node.js, но соответствие диапазонам не заменяет нашу сборку, typecheck и настоящие PostgreSQL-тесты. Источники: [системные требования](https://docs.prisma.io/docs/orm/reference/system-requirements) и metadata в таблице.

## Генерация и runtime

В [schema.prisma](../../packages/database/prisma/schema.prisma) используется генератор `prisma-client` с явными `output = "../src/generated"`, `moduleFormat = "esm"` и `importFileExtension = "js"`. Он выпускает TypeScript, который компилируется вместе с database package; сгенерированный `client.ts` используется серверным кодом. PostgreSQL-подключение передаётся через `PrismaPg` при создании клиента, с явно ограниченным pool. Генератор, адаптер и ESM-настройки описаны в [справочнике генераторов](https://docs.prisma.io/docs/orm/v7/prisma-schema/overview/generators) и [руководстве Prisma 7](https://docs.prisma.io/docs/guides/upgrade-prisma-orm/v7).

`src/generated` исключён из Git, ESLint, Prettier и входного Docker-контекста; [build database package](../../packages/database/package.json) сначала выполняет явную генерацию, затем `tsc`. Проверенные файлы поставщика содержат `eslint-disable`, `@ts-nocheck` и внутренние `any`. Это **явное исключение для неизменяемого кода генератора**, а не обещание отсутствия `any` во всех транзитивных исходниках. Код приложения, обёртки и публичные границы продолжают проверяться строгим TypeScript и запретом необоснованного `any`; `skipLibCheck: false` сохраняется. Ручное редактирование output не применяется: изменения должны воспроизводиться схемой, конфигурацией или обновлением генератора.

Обычный `generate` не требует работающей БД или URL. [prisma.config.ts](../../packages/database/prisma.config.ts) добавляет `datasource` только при заданном `DATABASE_MIGRATION_URL`; фиктивного или runtime URL по умолчанию нет. Это позволяет генерировать клиент без migration credentials, а команды, которым нужна БД, должны отказать без явной цели. `env()` здесь не используется: он бросает ошибку при загрузке config даже для генерации. Файлы `.env` Prisma 7 автоматически не загружает. Эти особенности подтверждает [справочник Prisma config](https://docs.prisma.io/docs/orm/v7/reference/prisma-config-reference).

## Lifecycle scripts и автономная сборка

Проверка clean deploy выявила дополнительную особенность pnpm 11: optional peer dependencies клиента связывали runtime с Prisma CLI и TypeScript. Удаление только peer declaration через override оставляло optional metadata, из которой pnpm восстанавливал связь `*`. Точный [readPackage hook](../../.pnpmfile.mjs) удаляет обе записи только для `@prisma/client@7.10.0`, предварительно проверяя optional flag. CLI и TypeScript остаются прямыми devDependencies; явные generate/build сохраняются. Hook входит в Docker и clean-copy inputs. Чистая frozen/offline установка, build и изолированный import прошли: database deploy содержит 23 пакета, без CLI/TypeScript; валидность PostgreSQL WASM проверена. Необходимость этого hook пересматривается при обновлении Prisma/pnpm.

В [pnpm-workspace.yaml](../../pnpm-workspace.yaml) дополнительно разрешены только `prisma@7.10.0` и `@prisma/engines@7.10.0`; существующее разрешение `esbuild@0.28.2` сохранено. CLI preinstall проверяет поддерживаемую версию Node. Postinstall engines скачивает schema-engine закреплённой версии для целевой платформы; runtime запросов использует JS/WASM compiler и `pg`. Исходники: [CLI preinstall](https://github.com/prisma/orm/blob/7.10.0/packages/cli/scripts/preinstall.ts), [engines postinstall](https://github.com/prisma/orm/blob/7.10.0/packages/engines/src/scripts/postinstall.ts).

Postinstall engines допускает тихий отказ скачивания, поэтому успешный `pnpm install` сам по себе не доказывает доступность CLI-артефактов. Windows-кэш не считается готовым Linux-кэшем. Автономная сборка должна отдельно подтвердить `generate --no-hints` с локальными пакетами/артефактами, без подключения к БД, затем build и import resolution; миграции проверяются на целевой платформе с реальной БД. `--no-hints` также исключает необязательное предложение установки Prisma agent skills, появившееся в 7.10.0. Проверки checksum/TLS не отключаются, общее разрешение lifecycle scripts не вводится.

## SQL-ограничения и migrations

`migrate deploy` применяет сохранённую migration history, не сбрасывает БД, не генерирует клиент и не использует shadow database. Он **не проверяет schema drift**. `migrate diff` сравнивает только возможности, представимые Prisma; отсутствие diff не доказывает сохранность triggers, RLS, CHECK constraints или физического partitioning. Источники: [deploy](https://docs.prisma.io/docs/cli/v7/migrate/deploy), [diff](https://docs.prisma.io/docs/cli/v7/migrate/diff), [предупреждения introspection](https://docs.prisma.io/docs/orm/v7/prisma-schema/introspection).

Для PHASE 2 Prisma schema описывает ORM-модели, а проверенные SQL migrations дополнительно задают ограничения, RLS/grants, неизменяемость evidence и partitions. Следующие изменения схемы должны сохранять этот SQL. Fresh/upgrade/repeat migrations и отдельные PostgreSQL-тесты проверяют фактические catalog definitions и поведение: tenant isolation под non-owner ролью, прямой SQL с недопустимыми значениями, partition bounds/pruning и ограничения записи. `db push` не является механизмом доставки этих изменений. Это проектное следствие ограничений ORM, зафиксированное в [требованиях PHASE 2](requirements.md).

## Сопровождение и безопасность

Выбор опирается на публичный [репозиторий Prisma ORM](https://github.com/prisma/orm), документацию и актуальный стабильный релиз, а не на обещание коммерческого SLA. В 7.10.0 опубликованы исправления очистки транзакций, обработки PostgreSQL deadlock/constraint errors и защиты локального Prisma Studio. Studio не становится частью runtime API. Лицензии прямых пакетов указаны по manifests; notices и лицензии транзитивных компонентов сохраняются при распространении.

Аудит расширенного графа 2026-09-07 обнаружил две high и одну moderate advisory. Введены узкие overrides только для зависимостей Prisma 7.10: `@prisma/config>deepmerge-ts=8.0.0` и `prisma>mysql2=3.23.1`. Повторный `pnpm audit --json` завершился с кодом 0: info/low/moderate/high/critical — 0; локальный отчёт `test-results/audit-phase2.json`. Порог CI не ослаблен, advisories не исключены.

Deepmerge 8.0.0 (BSD-3-Clause, Node >=16, 259 882 байта unpacked) исправляет рекурсию циклических графов. Это major override: изменена обработка Map и мутация входных данных; Prisma использует `deepmerge` для конфигурации из обычных объектов. Совместимость подтверждается выполнением validate/generate/deploy и последующими CI-проверками, а не одним audit. Источники: [advisory](https://github.com/advisories/GHSA-ggr8-5vv4-36mx), [release notes](https://github.com/RebeccaStevens/deepmerge-ts/releases/tag/v8.0.0).

MySQL2 3.23.1 (MIT, Node >=8, 573 475 байт unpacked) исправляет downgrade auth и ограничивает распаковку протокола. Проект использует PostgreSQL; MySQL2 приходит с CLI Prisma и не добавляет MySQL-сервис. Источники: [auth advisory](https://github.com/advisories/GHSA-3f6p-5ww8-9rcr), [исправление распаковки](https://github.com/sidorares/node-mysql2/releases/tag/v3.23.1). Оба override старше порога minimumReleaseAge; новых install lifecycle scripts не добавлено. Размер, лицензии, необходимость overrides и фактическую совместимость следует пересматривать при обновлении Prisma.
