# PHASE 3 — граница авторизации в PostgreSQL

Миграция [004](../../packages/database/prisma/migrations/202609140001_authentication/migration.sql) добавляет операции авторизации к модели PHASE 2. [005](../../packages/database/prisma/migrations/202609200001_auth_hardening/migration.sql) содержит отдельное PHASE 3 hardening: read/touch session paths, bounded recovery links, isolation guard, точные column grants и запрет TEMP для runtime. Опубликованные migrations 001–004 сохраняются без изменений. Регистрация всегда создаёт `User.role=USER`; публичного способа назначить `ADMIN` нет. Полный validation 005 отслеживается в [hardening verification](../phase-3-hardening/verification.md); исторический PASS 004 его не заменяет.

## Разделение ролей

| Назначение                | Возможности                                                                 | Ограничения                                                                           |
| ------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Migration LOGIN           | Применение версионированного DDL; передача владения auth-функциями          | Учетные данные доступны только инструменту миграций, не API                           |
| Runtime LOGIN → `ctp_api` | Обычные операции внутри `withTenant`; безопасные поля User, включая role    | Нет чтения passwordHash, tokenHash, секретов MFA; нет вызова auth-функций             |
| Auth LOGIN → `ctp_auth`   | EXECUTE на перечисленных публичных операциях схемы `ctp_auth`               | Нет доступа к исходным прикладным таблицам, вспомогательным функциям и роли владельца |
| `ctp_auth_owner`          | Владелец SECURITY DEFINER-функций; ограниченные необходимые табличные права | NOLOGIN, NOBYPASSRLS, без членства в других ролях, без CREATE после миграции          |

`ctp_auth` и `ctp_auth_owner` — выделенные NOLOGIN-роли, которым нельзя наследовать другие роли. Членство migration LOGIN в `ctp_auth_owner` имеет обратное направление и необходимо для передачи владения функциями. Startup/readiness отклоняет смешение API/auth-ролей, владельцев таблиц, привилегированные логины, опасное наследование, database/schema CREATE, database TEMP и прямые прикладные column/table grants auth LOGIN. Runtime API не может получить secret column даже через прямой grant конкретному LOGIN. Readiness требует auth schema version 5 и FORCE RLS на User, sessions, verification/reset tokens, MFA config и LIVE grants. Ошибка выдаётся безопасным кодом без SQL, DSN или параметров запроса.

005 отзывает PostgreSQL default PUBLIC TEMP для текущей БД. Это migration-owner DDL над известным `current_database()`, quoted как identifier; SQL из пользовательского ввода не строится. Runtime роли не создают временные объекты. Отдельный negative fixture создаёт shadow tables привилегированным владельцем и затем переключается на auth role: даже при таком caller search_path функции обязаны читать полностью квалифицированные реальные таблицы.

Все auth-функции используют `search_path=pg_catalog`, полные имена прикладных таблиц и фиксированные SQL-операции. PUBLIC EXECUTE отзывается до COMMIT. Только перечисленные внешние операции получают EXECUTE для `ctp_auth`; вспомогательные функции остаются недоступными. Роль владельца не получает чтение ciphertext MFA, recovery-code hashes или exchange credentials. Для MFA доступны только tenantId, enabledAt и revokedAt; для LIVE grants — поля, необходимые для отзыва.

Права SELECT/INSERT/UPDATE владельца перечислены по колонкам: новая колонка не становится автоматически доступна. [Проверка effective privileges](../../packages/database/src/auth-role-boundary.ts) выявляет лишние column grants, role promotion/step-up writes, secret access, private function exposure, неверного function owner, PUBLIC EXECUTE и drift search_path. Это защита от provisioning drift; migration/cluster administrator остаётся доверенной стороной.

FORCE RLS остаётся включённым. Предтенантный поиск по email и хэшу токена выполняют функции владельца с отдельной явно адресованной RLS-политикой на нужных таблицах. Это доверенная граница, необходимая до появления principal; она не выдаёт auth LOGIN произвольный SQL-доступ. Обычные пользовательские запросы после авторизации используют principal.userId через `withTenant`, а не tenantId из HTTP-параметров.

## Переходы и конкуренция

Пароли хэширует Argon2id в пакете auth; PostgreSQL принимает PHC-строку, но не реализует проверку пароля. Результат проверки вне БД подтверждается в `create_session`: под блокировкой User сравниваются актуальные passwordHash и sessionEpoch, проверяются ACTIVE, verified email и требование MFA. Поэтому сброс пароля или logout-all, завершившийся во время вычисления Argon2id, не позволяет создать сессию по старым credentials.

В SQL поступают только 32-байтовые SHA-256-хэши непрозрачных токенов. Сроки определяет время PostgreSQL: email verification — 30 минут, password reset — 15 минут, idle session — 30 минут, absolute session — 12 часов. При locking transitions время перечитывается после получения блокировок. Проверка сессии не продлевает абсолютный срок. Ротация отзывает старую запись и создаёт новую с прежним абсолютным сроком; параллельный replay старого токена может завершиться успехом только один раз.

В 005 большинство authenticate — read-only проверка session/User/epoch/MFA одним свежим READ COMMITTED snapshot. После пяти минут требуется touch: User → session lock, повторная проверка eligibility/expiry и conditional UPDATE. Параллельные due touches перечитывают lastSeenAt под lock; абсолютный срок не увеличивается, idle expiry не оживает. Idle deadline может отставать от последнего чтения до пяти минут, так что новая модель консервативно сокращает период бездействия, а не расширяет доступ. Список сессий авторизуется одним snapshot вместе с returned records.

Чтение, начавшееся до commit параллельного revoke/reset/MFA/status transition, может завершиться по прежнему допустимому snapshot; чтение после commit видит новое состояние. Это не разрешение выполнить позднее sensitive write: такой writer обязан заново проверить principal/epoch/assurance внутри своей locking transaction. Auth pool явно задаёт READ COMMITTED; SQL entrypoints отклоняют REPEATABLE READ/SERIALIZABLE с `25001`, включая unknown identities/tokens, чтобы caller-owned snapshot не обходил MFA и epoch changes.

Все изменения существующего security state сначала блокируют User. Затем они повторно читают и при необходимости блокируют соответствующий token/session. Verification и reset одноразовые. Выдача допускает максимум три активные ссылки каждого вида с cooldown 60 секунд; прежняя живая ссылка не потребляется и не вытесняется неаутентифицированным resend. При исчерпанном cooldown/cap возвращается generic accepted без нового письма. Expired, consumed и reset tokens прежнего epoch не расходуют current active capacity. Logout идемпотентен; revoke проверяет владельца; logout-all увеличивает sessionEpoch и отзывает все сессии.

Password reset и password change в одной SQL-транзакции изменяют пароль, увеличивают sessionEpoch, отзывают сессии, потребляют reset tokens и отзывают все действующие LIVE grants этого tenant. Grants другого пользователя сохраняются. Это соединяет восстановление доступа в PHASE 3 с моделью разрешений LIVE из PHASE 0–2. Сброс пароля не отключает MFA, не меняет роль и не создаёт сессию.

`ADMIN` и аккаунт с включённой непрекращённой MFA не получают сессию до реализации проверяющей MFA-ветки. Уже выданная сессия такого аккаунта тоже не проходит authenticate. После ожидания User lock MFA перечитывается; READ COMMITTED guard не позволяет caller-owned historical transaction отменить это свойство.

Будущие операции изменения роли, статуса, MFA и публикации LIVE grant обязаны сначала блокировать тот же User и затем повторно проверять актуальную сессию, epoch и необходимые условия. Блокировка только строки MFA либо grant не обеспечивает согласования со сбросом пароля. Полноценная TOTP/recovery-проверка, выдача LIVE-разрешений и workflow удаления аккаунта не объявляются реализованными этой миграцией.

## Применение и проверка

Роли PostgreSQL существуют на уровне кластера и переживают удаление отдельной БД. При первом создании `ctp_auth_owner` миграция выдаёт выполняющему её владельцу необходимое членство. Если роль уже создана другой БД, администратор кластера предварительно выдаёт конкретному migration LOGIN право SET в `ctp_auth_owner`. Runtime LOGIN такое членство получать не должен. Миграция не повышает runtime до BYPASSRLS и не снимает FORCE RLS для передачи функций.

[Изолированный runner](../../scripts/test-database.mjs) выполняет fresh/repeat deploy, upgrade с сохранением данных, измерение опубликованной 004 и переход к 005, non-SUPERUSER/non-BYPASS owner, SQL/Redis suite и compiled API с раздельными логинами. После этого он пересоздаёт только собственную временную БД и повторяет migration deploy. DDL ограничен 30 секундами на сервере; auth statement timeout — 3 секунды, client timeout — 3,5 секунды, pool — 3 соединения, close — 8 секунд. Наличие сценария в runner само по себе не означает PASS.

[Security integration tests](../../packages/database/test/auth.integration.test.ts) проверяют права, FORCE RLS, владельцев/search_path/PUBLIC EXECUTE, утечки диагностики, replay, idle/absolute expiry, чужие сессии, reset/change-password, отзыв LIVE grants, ADMIN/MFA и реальные гонки при блокировке User. Проверка смены inherited privileges дополнительно убеждается, что readiness отклоняет изменённую после старта границу владельца функций.

Исторический запуск 20 сентября 2026 для 004: 110 PostgreSQL + 12 Redis tests PASS, compiled auth flow 46 HTTP requests PASS, shutdown 36 ms, отдельный Docker smoke PASS. Подробности сохранены в [историческом отчёте PHASE 3](verification.md). Эти значения не относятся автоматически к 005; текущие результаты и ограничения публикуются отдельно в [hardening verification](../phase-3-hardening/verification.md).

## Retention перед production

Security TTL исключает просроченный credential из authentication, но не удаляет строку. Сейчас scheduled cleanup отсутствует: таблицы и indexes растут. Обязательная production policy — expired/consumed verification/reset tokens сохраняются минимум семь дней после более позднего expiresAt/consumedAt; revoked/expired sessions — минимум 30 дней после последнего применимого deadline/revoke. Active records не удаляются, audit evidence хранится отдельно. Будущий job использует отдельную maintenance role, bounded batches/lock timeouts, dry-run counts, progress/error metrics и vacuum/index monitoring; runtime auth не получает DELETE. Реализация и boundary/concurrency tests этого job остаются production prerequisite, а не частью уже доказанного auth TTL.
