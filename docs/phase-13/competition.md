# Bounded PAPER competition calculation

This PHASE 13 increment starts from protected main **dc8aa954bebe9a6c0d297d6369a92535e9522a41**. That main accepted readonly market frames and final-return expiry hardening through PRs #8–9, complete [CI 38226761988](https://github.com/dendenden-boop/tradeGPTbot/actions/runs/38226761988) and [CodeQL 38226760693](https://github.com/dendenden-boop/tradeGPTbot/actions/runs/38226760693). This increment implements only deterministic arbitration of competing orders in a single pure calculation. It does not implement durable allocation or financial execution. Published migrations 1–39, lockfile, existing financial runtime, market frames, individual-order calculator and workflows remain unchanged.

## Inputs and priority

`calculatePaperCompetition` on the pure `@ctp/paper-engine` root accepts a strict `{ now, frame, orders }` object. It returns version `spot-l2-admission-fifo-v1`, ordered execution calculations and one final frame. Each candidate has exact `orderId`, `admissionSequence`, original `NewOrder`, submission time, previously executed quantity and nullable triggered time. Unknown fields, including tenant, grants, credentials and URLs, reject. A batch contains 1–300 orders and at most 1000 levels on each book side. Collection lengths are checked before walking individual entries; there is no asynchronous queue, background work or transport.

Priority is ascending positive signed-64-bit `admissionSequence`, represented by a canonical integer string and compared with BigInt. UUID order IDs normalize to lowercase. Duplicate sequence, order ID or exact clientOrderId rejects the entire batch. Sequence gaps are allowed; zero, signs, leading zeros, Number inputs and overflow reject. Candidate input order, local arrival time and UUID do not change allocation priority. Submission time determines modeled latency rather than priority.

The eventual server worker must assign and persist this account/scenario sequence with the accepted immutable intent. A caller-provided number is not evidence of durable admission order. Each batch belongs to one exact server-owned tenant/account/reset/model scenario and one native source/instrument/trade frame; this pure interface neither certifies that ownership nor authorizes cross-account aggregation. The future gateway must reconstruct all candidates from authoritative storage, select the permitted scenario and verify permanent replay before applying any result.

The future worker must select the complete eligible candidate set or an authoritative bounded continuation in the same priority order with the same persisted consumption checkpoint. Choosing an arbitrary subset or preparing a fresh zero-used frame between batches cannot authorize priority or volume reset. The 300 bound is a per-calculation resource limit, not a claim that global scheduling, concurrent workers or durable account capacity have been implemented.

## Shared calculation budget

The function reuses the accepted `evaluatePaperOrder` model unchanged. After each candidate, its next frame becomes the input for the next candidate. BUY and SELL therefore share the native trade quantity × participation cap, rounded to lot size, while each book level retains its own observed depth cap. A supplied already-consumed calculation checkpoint remains consumed. The result omits intermediate frames from individual executions and returns one deeply immutable final frame; caller input remains unchanged.

An order awaiting latency, an untriggered STOP, a completed order or failed FOK consumes no new volume and does not prevent a subsequent eligible order from using it. Successful FOK consumes the whole remaining quantity; IOC preserves its existing partial-fill/expiry behavior. Seeded slippage, adverse tick rounding, quote fees, fill identities, rules validation and no-lookahead evidence requirements remain those of the individual-order model. Stale evidence rejects even a completed-order-only batch. If any later candidate has invalid rules, unsupported semantics or inconsistent state, the entire pure calculation throws without returning partial executions or changing input.

## Replay and authority limitations

Identical serialized inputs and input permutations reproduce the same result. This is a calculation property, **not durable replay, restart recovery or a transaction**. The frame and sequence are calculation inputs, not Risk grants, reservations, Portfolio commitments, transport permits or authenticated database receipts. The function reads no account, controls, policy, balance, reservation or native credentials and performs no financial write.

Running the same batch again on a fresh zero-used frame could calculate the same fills again. Replacing a book while retaining a native trade could also reset a caller's calculation budget. Neither operation grants fresh money or volume authority. The still-outstanding durable worker must bind permanent native trade identity independently of publication ID/rules refresh; conserve shared BUY/SELL consumption across book changes; preserve order/event replay and priority after restart; and commit allocation, order result, reservation/hold and balanced ledger postings in one bounded transaction. Ambiguous COMMIT must return no grant and resolve from authoritative durable state. Do not compose a standalone volume grant followed by a separate monetary transaction.

Certified PAPER Risk, current final dispatch validation, durable shared liquidity, native feed/GAP recovery, conditional exits, positions/PnL and reset remain outstanding. PAPER dispatch and LIVE remain disabled. Native AMEND remains accepted only for Binance Spot TESTNET; positive native collateral credit is disabled. Real private exchange tests and production soak are not claimed. **PHASE 13 IN_PROGRESS / NOT READY FOR PHASE 14**.
