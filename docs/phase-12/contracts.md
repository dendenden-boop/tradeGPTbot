# PHASE 12 contracts

Current cross-phase [runtime InstrumentRegistry contract](runtime-instrument-registry.md) separates bounded observational metadata projections from authoritative PostgreSQL current reads and atomic durable version history. Its complete native/OS/Docker acceptance is recorded in verification; it is not a completed Risk certificate or mutation grant.

## PostgreSQL physical acquisition lifecycle

Market store/snapshots, Portfolio, Order and the four Risk source/control/policy ports own their physical TCP stream before PostgreSQL authentication. Shared acquisition has four physical slots and four explicitly owned waiting slots, with an absolute acquisition bound of three seconds or the earlier caller deadline. Waiting callers do not enter pg's hidden queue. Abort destroys a connecting socket, rejects an owned waiting acquisition and prevents late publication. Handshake listeners/timers are detached on settlement so the original caller cannot destroy a subsequently reused idle connection. Close cancels owned waiters, destroys active/idle/connecting streams and waits for actual settlement. This helper has no SQL or monetary authority; existing transaction locks and privilege checks remain authoritative.

Market/Portfolio success additionally requires an unexpired, nonaborted context after known COMMIT. An aborted or uncertain response does not prove rollback. Market recovers its durable checkpoint/outbox; Portfolio replays the exact permanent event and retains UNKNOWN collateral. Neither path blindly repeats a monetary effect or releases on a missing acknowledgement. Native response-loss acceptance is required separately from finite wire fixtures.

Checked-out pg clients retain one owned error listener through connection loss and idle reuse. It prevents an unhandled driver event; the query still rejects, the failed client becomes unqueryable and is discarded. Raw driver errors are not logged or returned as authority.

## Durable UTC loss source

createPostgresLossJournal requires a server-controlled PostgreSQL URL and an isolated ctp_risk_evidence_collector login. This role has only append_loss_batch/read_loss_checkpoint function authority. It has no table, policy, execution, Portfolio or monetary writer grants. Direct function callers face the same SQL role/input restrictions; factory checks do not stand in for SQL checks.

The permanent batch UUID precedes current sequence validation. Exact replay returns the original immutable checkpoint; semantic conflict rejects. Individual native observation/economic event UUIDs are permanent across batches/modes/days for that tenant. New batches require the current loss head sequence and contiguous coverage from its coveredThrough. GLOBAL shared then tenant exclusive locks serialize publisher CAS; reads use GLOBAL shared then tenant shared. Explicit READ COMMITTED, physical abort/deadline destruction and known COMMIT precede a successful result; uncertain COMMIT returns no result and recovery uses the same permanent batch identity.

Opening is allowed only when no daily head exists, at the exact UTC midnight, with independently reconciled opening/coverage source identities and hashes. A continuation cannot replace it, skip a history interval or finish after an unvalued flow. Events have explicit ordering even at equal timestamps, and the final event must be an EQUITY mark at coveredThrough. Fresh publication is bounded to five seconds. FLOW changes externalFlows; REALIZED is net of fees/funding in the explicit valuation currency; EQUITY minus accumulated FLOW determines current adjusted equity. Peak includes the immutable opening and every adjusted mark. The publisher must obtain these from complete native/Portfolio evidence; raw client values and hashes are not trusted sources.

Immutable history lives in PostgreSQL; one current checkpoint is read without loading an unbounded journal into process memory. Per-batch limits are 1000 events/262144 bytes; exact counters use PostgreSQL bigint and money uses the existing 30-integer/18-fraction canonical envelope. Capacity/overflow rejects the entire transaction. Missing day/mode/currency has no fallback or guessed opening. Deployment/reset does not synthesize evidence. This component does not create a certificate, grant, reservation, hold or ledger posting. The full source backend and atomic integrations remain required.

Coordinator reconstruction consumes either a reference UTC event history or the durable constant-size LossCheckpoint. For a checkpoint its source reference must exactly match batchId, lossless sequence and coveredThrough; the source content hash still covers the complete value. consumeLossCheckpoint requires the exact tenant/storage mode/valuation currency, current UTC midnight/day, a final mark within the effective policy freshness window and a peak at least equal to opening/current adjusted equity. It preserves the already adjusted current/peak and net realized result verbatim; external flows are never subtracted twice. A replacement durable loss head invalidates readCurrent across coordinator restart. The physical source transaction must read and verify the immutable checkpoint text/hash and current head, with all other source locks held; this pure consumption helper does not prove native history or manufacture a PostgreSQL certificate backend.

Permanent event identities, contiguous lossless integer sequences, nonregressing timestamps and a current equity mark after the last external flow are required. External deposits/withdrawals are signed FLOW events; adjusted equity at each EQUITY event is equity minus cumulative external flows, and adjusted peak is the maximum of those observations and opening equity. ## Trust and policy evaluation

Bindings, policies, capabilities, market state, accounting totals, loss baselines and classification come from authorized server composition. Strict schemas prove shape and scope, not authenticity. No client-provided snapshot can authorize an order. The pure evaluator returns EVALUATED or REJECTED with stable reason codes and a conservative reservation proposal; neither result contains a durable decision ID, reservation ID or transport permission. The PHASE 11 OrderRiskPort continues requiring an independently persisted RiskGrant.

Effective maximum limits use the tighter platform/user value; minimum balance/liquidity protections use the larger. Both policies are mandatory and have the same valuation asset. Values are exact canonical decimals without Number conversion or implicit rounding. Unsupported scale/range in an intermediate calculation rejects. Inputs are not normalized into changed commands. The existing Core registry admission remains authoritative for step/tick/notional/unsupported filters.

The first increment supports BASE quantity MARKET/LIMIT for Spot and linear perpetual NET instruments. Conditional, contract-quantity, inverse and dated instructions fail closed until their effect models are separately implemented. MARKET requires a proved execution-price bound, not an estimate from visible depth alone. Quantity multiplied by the lower/upper bound must satisfy native notional filters. Capability records use existing Core exact-profile/version/expiry/native-implementation checks; a boolean request flag never enables a feature.

Spot BUY proposal is limit/bounded quote principal plus the proved maximum quote fee; Spot SELL proposal is base quantity plus a proved maximum base fee. Unknown or third-asset fee models reject in this increment. Increasing linear derivatives conservatively propose full quote notional plus fees, with no unproved leverage discount; reduction proposes fees only after native reduce-only and remaining-position checks. These proposals are deliberately conservative calculations, not exchange margin estimates. The future certified collateral model must prove alternative savings before they can replace this bound. Available balance is in the proposal asset; protection after the proposal is converted using fresh explicit evidence and the lower base-price bound where needed.

Loss inputs are coordinator-proved adjusted opening/current/peak equity and UTC-day realized net PnL. Positive loss reaching its cap blocks new risk; zero actual loss does not invent a loss solely because the configured cap is zero. Nonpositive or incomplete baselines, old UTC intervals and peaks below opening/current equity reject. This increment verifies the supplied evidence shape and arithmetic; it does not reconstruct external flows or persist a high-watermark.

Market and accounting evidence must match the complete tenant/account/storage mode/profile/instrument and currency scope. Exposure inputs include positions and every pending/unknown commitment exactly once, supplied by the future certified coordinator. Losses and exposure are in valuationAsset. Price bounds/reference/bid/ask are **native quote-asset prices per base unit**, proved by priceAsset matching the instrument quote; native filters use these prices before conversion. Order notional is converted once by quoteToValuation. liquidityNotional is already in explicit liquidityAsset, which must equal valuationAsset; the coordinator must preserve its conversion provenance. Both liquidity comparisons use valuationAsset. FX carries fxFromAsset/fxToAsset, source ID, timestamp and kind: IDENTITY requires equal assets and rate 1; distinct assets require OBSERVED evidence even for stablecoins. Missing/contradictory currency or stale/future FX rejects. Policy evaluation checks shape/freshness, but does not certify a source or advance its persisted revision.

positionEvidence binds the proved native account mode and SPOT/ONE_WAY/HEDGE classification to account, instrument, certified source ID/revision, timestamp and exact signed quantity. The current model requires NET side and ONE_WAY for derivatives, with exact adapter account modes BINANCE ONE_WAY, BYBIT UTA2_ONE_WAY or OKX FUTURES_MODE_NET. HTX SINGLE_ASSET_CROSS_HEDGE is rejected even when an input claims ONE_WAY. Missing evidence, LONG/SHORT aggregation, conflicting quantity/scope/revision and stale/future mode evidence reject. Tests use real adapter profiles and native instrument normalizers; OKX swap contract quantities remain unsupported. These schemas do not certify caller-supplied evidence.

Execution startup requires EXECUTE on exactly ctp_risk.dispatch_gate(uuid,uuid). Every additional executable ctp_risk function or overload, including an unknown future function or PUBLIC/inherited grant, rejects with ORDER_DATABASE_ROLE_UNSAFE. Protected schema ownership/CREATE and Risk table/column writes are forbidden, so the execution login cannot manufacture a new function after startup. Updating a future final-gate signature requires an explicit reviewed allowlist change; adding a function cannot silently expand execution authority.

Instrument exposure is a subset of the account's exposure to that base asset, which is a subset of account exposure, itself a subset of same-mode user exposure. Reversed totals fail closed even with complete=true. Spot has no implicit short/borrowing model. A nonzero position requires a positive concurrent-position count; a pending instrument entry requires a positive open-order count. These consistency checks supplement, rather than replace, certified source completeness.

Increasing risk requires all critical health checks closed/healthy, current metadata/capability, reconciled positions/balances and fresh complete valuation. Pauses and half-open circuits reject. Derivative reduction additionally requires native reduce-only capability, matching signed NET position, and quantity no greater than the position minus all competing reduction commitments. Unsupported Spot reduce-only, hedge, inverse and uncertain position evidence reject. Reduction is separately evaluated; it never exempts rules, auth, physical infrastructure, fee/collateral or liquidity safety.

## Durable controls and dispatch ordering increment

The new SQL-owned ctp_risk schema separates GLOBAL operator authority from tenant USER/CONNECTION/STRATEGY authority. Neither role can mint risk grants, write Portfolio money or dispatch. Scope IDs are composed by authorized server code; accepting a UUID shape is not tenant authorization. There is no public HTTP control endpoint. Tenant writes require an exact current app.tenant_id, an owned existing scope and the tenant-controller role. Only the separate operator role can change global controls. Execution has function-only access to the final gate and no control-write authority.

Every update has a permanent event UUID, expected current epoch, desired state, bounded reason and evidence fingerprint. Exact replay returns the original event, including its historical epoch; it is not a current-state read. A conflicting replay rejects. New updates compare-and-swap the durable head and advance its integer epoch exactly once; an old resume cannot replace a newer pause, including across restart or A→B→A. Immutable events and nondeletable monotonic heads retain the watermark. No wall-clock ordering, TTL auto-resume or process-local reset is permitted. Epochs use canonical bigint-safe strings and reject exhaustion.

GLOBAL starts PAUSED on fresh deploy and upgrade. An operator must explicitly initialize/resume it with evidence; migration never opens dispatch. Missing or contradictory global state rejects. Tenant scopes without any event are RUNNING/CLOSED baseline states under the durable global gate. GLOBAL and all owned tenant controls compose conjunctively. HALF_OPEN permits future infrastructure/reconciliation probes only; it never permits an order. Closing a circuit or resuming requires a fresh epoch and an authorized evidence-bearing update; this storage module does not certify probe health by itself.

Pause updates and final one-use transport permission share PostgreSQL transaction advisory locks: global first, tenant second, before account locks. Global updates take an exclusive global lock; tenant updates take shared global then exclusive tenant; dispatch takes both shared locks through permit consumption and COMMIT. Locks only order short SQL transactions, never HTTP. A consumed permit committed before a pause is causally earlier and an already dispatched operation cannot be retroactively canceled by a pause. A pause that commits first prevents subsequent permit consumption. Abort/deadline destroys the underlying SQL connection within the existing bounded transport contract; uncertain COMMIT returns no permission. Reconciliation must retain possibly dispatched reservations.

The PHASE 11 placement/cancellation gate conservatively rejects every mutation under any relevant pause/nonclosed circuit. It does not trust reduceOnly or infer whether cancellation removes protection. Because existing PHASE 11 commands have no strategy identity, any blocked strategy in the tenant also blocks these unclassified commands. Exact strategy classification, independently proved reductions/protective cancellation, current policy/state certification and AMEND remain acceptance work; no guessed exception is enabled. Existing public trading_pause and circuit_state records are additional conservative blockers, not silently ignored or rewritten.

## AMEND semantic design

An amendment names one existing internal order, original placement identity, native identity, account/mode/profile/instrument and observed server revision. Original PLACE command remains immutable. Revised quantity means **total cumulative target quantity**, not unfilled remainder. New quantity must exceed proved executed quantity at evaluation; fills racing dispatch can still cause a terminal native result and require reconciliation. Changing side, instrument, account, position side, reduce-only intent or order type is a new order, not amendment.

IN_PLACE and CANCEL_REPLACE are distinct semantics. IN_PLACE preserves the native order identity but may change queue priority. CANCEL_REPLACE has separate original-cancel and replacement-place outcomes and identities; it is never reduced to one generic success boolean. A transport cannot silently choose between them. No replacement is dispatched after an unproved cancel result. A rejection that also canceled the original is a distinct terminal observation, not a definitive no-effect rejection.

ACK means receipt only. Positive native amendment evidence must identify the requested revision/parameters and causal fills; a generic getOrder response that happens to match is insufficient to prove which concurrent amendment applied. Missing native request/revision correlation, lost response or partially successful replace remains UNKNOWN/reconciliation-required, never retried blindly. New risk is reserved conservatively before mutation and released only after proved outcomes. Unsupported mappings remain fail-closed.

Official sources reviewed 2026-10-05: [Bybit ordinary order amendment](https://bybit-exchange.github.io/docs/v5/order/amend-order) is asynchronous; [OKX](https://www.okx.com/docs-v5/en/) defines cumulative newSz, terminal behavior when quantity meets prior fills, optional cancel-on-fail and asynchronous amendment outcome; [Binance Spot](https://github.com/binance/binance-spot-api-docs/blob/master/rest-api.md) distinguishes cancel/replace partial outcomes and keep-priority quantity reduction. These are capability constraints, not proof that the current adapters implement amendment. No Core mutation DTO or production feature flag is enabled by this design increment.

Rechecked 2026-10-06 against the official [Binance keep-priority FAQ](https://raw.githubusercontent.com/binance/binance-spot-api-docs/master/faqs/order_amend_keep_priority.md): native in-place amendment permits quantity reduction, retains the order ID, requires symbol amendAllowed=true, can change clientOrderId and exposes amendment history. OCO amendment changes both legs. Therefore a future first accepted profile must prove standalone order identity and native eligibility, persist each new client identity and correlate history with its immutable AMEND intent. The current locator/replacement DTO alone cannot prove this lifecycle; AMEND remains UNSUPPORTED rather than silently dispatching a coupled or cancel/replace mutation.

## PostgreSQL Portfolio authority read port

Old hold timestamps do not automatically release held money.

The returned PORTFOLIO_SOURCE carries a stable content/revision-vector hash and the minimum original snapshot time. Read time, cache receipt and restart do not refresh it. Hash validates content, not source authorization. Its type deliberately has no complete certificate, health, tradeAllowed or grant field. The SQL locks persist through the reader transaction only. The full RiskSnapshotStore must reuse authoritative collection within its own certificate transaction, prove complete concurrent inventory/order/reservation coverage and compose all nine source families; it must not certify a collection of separately committed reader calls. This read port alone has no current policy/rule/capability/position-mode/FX/health proof and cannot authorize an order. LIVE dispatch remains disabled.

Additive migration 202610070004_portfolio_capture_inventory replaces only the capture function body, preserving its signature/owner/reader grant and published migrations.
