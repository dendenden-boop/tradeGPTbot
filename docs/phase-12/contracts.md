# PHASE 12 contracts

## Trust and policy evaluation

Bindings, policies, capabilities, market state, accounting totals, loss baselines and classification come from authorized server composition. Strict schemas prove shape and scope, not authenticity. No client-provided snapshot can authorize an order. The pure evaluator returns EVALUATED or REJECTED with stable reason codes and a conservative reservation proposal; neither result contains a durable decision ID, reservation ID or transport permission. The PHASE 11 OrderRiskPort continues requiring an independently persisted RiskGrant.

Effective maximum limits use the tighter platform/user value; minimum balance/liquidity protections use the larger. Both policies are mandatory and have the same valuation asset. Values are exact canonical decimals without Number conversion or implicit rounding. Unsupported scale/range in an intermediate calculation rejects. Inputs are not normalized into changed commands. The existing Core registry admission remains authoritative for step/tick/notional/unsupported filters.

The first increment supports BASE quantity MARKET/LIMIT for Spot and linear perpetual NET instruments. Conditional, contract-quantity, inverse and dated instructions fail closed until their effect models are separately implemented. MARKET requires a proved execution-price bound, not an estimate from visible depth alone. Quantity multiplied by the lower/upper bound must satisfy native notional filters. Capability records use existing Core exact-profile/version/expiry/native-implementation checks; a boolean request flag never enables a feature.

Spot BUY proposal is limit/bounded quote principal plus the proved maximum quote fee; Spot SELL proposal is base quantity plus a proved maximum base fee. Unknown or third-asset fee models reject in this increment. Increasing linear derivatives conservatively propose full quote notional plus fees, with no unproved leverage discount; reduction proposes fees only after native reduce-only and remaining-position checks. These proposals are deliberately conservative calculations, not exchange margin estimates. The future certified collateral model must prove alternative savings before they can replace this bound. Available balance is in the proposal asset; protection after the proposal is converted using fresh explicit evidence and the lower base-price bound where needed.

Loss inputs are coordinator-proved adjusted opening/current/peak equity and UTC-day realized net PnL. Positive loss reaching its cap blocks new risk; zero actual loss does not invent a loss solely because the configured cap is zero. Nonpositive or incomplete baselines, old UTC intervals and peaks below opening/current equity reject. This increment verifies the supplied evidence shape and arithmetic; it does not reconstruct external flows or persist a high-watermark.

Market and accounting evidence must match the complete tenant/account/storage mode/profile/instrument and currency scope. Exposure inputs include positions and every pending/unknown commitment exactly once, supplied by the future certified coordinator. Price bounds, losses and exposure must already be expressed in the declared common valuation asset; no stablecoin parity or unproved FX conversion is allowed. Policy evaluation checks their freshness and completeness, but does not certify a source or advance its persisted revision.

Instrument exposure is a subset of the account's exposure to that base asset, which is a subset of account exposure, itself a subset of same-mode user exposure. Reversed totals fail closed even with complete=true. Spot has no implicit short/borrowing model. A nonzero position requires a positive concurrent-position count; a pending instrument entry requires a positive open-order count. These consistency checks supplement, rather than replace, certified source completeness.

Increasing risk requires all critical health checks closed/healthy, current metadata/capability, reconciled positions/balances and fresh complete valuation. Pauses and half-open circuits reject. Derivative reduction additionally requires native reduce-only capability, matching signed NET position, and quantity no greater than the position minus all competing reduction commitments. Unsupported Spot reduce-only, hedge, inverse and uncertain position evidence reject. Reduction is separately evaluated; it never exempts rules, auth, physical infrastructure, fee/collateral or liquidity safety.

## Durable gateway required before acceptance

Evaluate-and-reserve must reread certified versions and permanent intent ownership inside stable SQL locks; pure EVALUATED is only an input to that transaction. The transaction owns aggregate risk budgets and immutable decision/reservation evidence, not Portfolio monetary postings. Release requires authoritative definitive evidence; UNKNOWN retains its reservation even after deadline. Final dispatch and pause updates share a durable ordering gate. An earlier policy result never permits bypassing permission revocation, changed rules or current pauses. Physical SQL abort, unknown commit and restart are explicit acceptance cases.

## Durable controls and dispatch ordering increment

The new SQL-owned ctp_risk schema separates GLOBAL operator authority from tenant USER/CONNECTION/STRATEGY authority. Neither role can mint risk grants, write Portfolio money or dispatch. Scope IDs are composed by authorized server code; accepting a UUID shape is not tenant authorization. There is no public HTTP control endpoint. Tenant writes require an exact current app.tenant_id, an owned existing scope and the tenant-controller role. Only the separate operator role can change global controls. Execution has function-only access to the final gate and no control-write authority.

Every update has a permanent event UUID, expected current epoch, desired state, bounded reason and evidence fingerprint. Exact replay returns the original event, including its historical epoch; it is not a current-state read. A conflicting replay rejects. New updates compare-and-swap the durable head and advance its integer epoch exactly once; an old resume cannot replace a newer pause, including across restart or A→B→A. Immutable events and nondeletable monotonic heads retain the watermark. No wall-clock ordering, TTL auto-resume or process-local reset is permitted. Epochs use canonical bigint-safe strings and reject exhaustion.

GLOBAL starts PAUSED on fresh deploy and upgrade. An operator must explicitly initialize/resume it with evidence; migration never opens dispatch. Missing or contradictory global state rejects. Tenant scopes without any event are RUNNING/CLOSED baseline states under the durable global gate. GLOBAL and all owned tenant controls compose conjunctively. HALF_OPEN permits future infrastructure/reconciliation probes only; it never permits an order. Closing a circuit or resuming requires a fresh epoch and an authorized evidence-bearing update; this storage module does not certify probe health by itself.

Pause updates and final one-use transport permission share PostgreSQL transaction advisory locks: global first, tenant second, before account locks. Global updates take an exclusive global lock; tenant updates take shared global then exclusive tenant; dispatch takes both shared locks through permit consumption and COMMIT. Locks only order short SQL transactions, never HTTP. A consumed permit committed before a pause is causally earlier and an already dispatched operation cannot be retroactively canceled by a pause. A pause that commits first prevents subsequent permit consumption. Abort/deadline destroys the underlying SQL connection within the existing bounded transport contract; uncertain COMMIT returns no permission. Reconciliation must retain possibly dispatched reservations.

The PHASE 11 placement/cancellation gate conservatively rejects every mutation under any relevant pause/nonclosed circuit. It does not trust reduceOnly or infer whether cancellation removes protection. Because existing PHASE 11 commands have no strategy identity, any blocked strategy in the tenant also blocks these unclassified commands. Exact strategy classification, independently proved reductions/protective cancellation, current policy/state certification and AMEND remain acceptance work; no guessed exception is enabled. Existing public trading_pause and circuit_state records are additional conservative blockers, not silently ignored or rewritten.

## AMEND semantic design

An amendment names one existing internal order, original placement identity, native identity, account/mode/profile/instrument and observed server revision. Original PLACE command remains immutable. Revised quantity means **total cumulative target quantity**, not unfilled remainder. New quantity must exceed proved executed quantity at evaluation; fills racing dispatch can still cause a terminal native result and require reconciliation. Changing side, instrument, account, position side, reduce-only intent or order type is a new order, not amendment.

IN_PLACE and CANCEL_REPLACE are distinct semantics. IN_PLACE preserves the native order identity but may change queue priority. CANCEL_REPLACE has separate original-cancel and replacement-place outcomes and identities; it is never reduced to one generic success boolean. A transport cannot silently choose between them. No replacement is dispatched after an unproved cancel result. A rejection that also canceled the original is a distinct terminal observation, not a definitive no-effect rejection.

ACK means receipt only. Positive native amendment evidence must identify the requested revision/parameters and causal fills; a generic getOrder response that happens to match is insufficient to prove which concurrent amendment applied. Missing native request/revision correlation, lost response or partially successful replace remains UNKNOWN/reconciliation-required, never retried blindly. New risk is reserved conservatively before mutation and released only after proved outcomes. Unsupported mappings remain fail-closed.

Official sources reviewed 2026-10-05: [Bybit ordinary order amendment](https://bybit-exchange.github.io/docs/v5/order/amend-order) is asynchronous; [OKX](https://www.okx.com/docs-v5/en/) defines cumulative newSz, terminal behavior when quantity meets prior fills, optional cancel-on-fail and asynchronous amendment outcome; [Binance Spot](https://github.com/binance/binance-spot-api-docs/blob/master/rest-api.md) distinguishes cancel/replace partial outcomes and keep-priority quantity reduction. These are capability constraints, not proof that the current adapters implement amendment. No Core mutation DTO or production feature flag is enabled by this design increment.
