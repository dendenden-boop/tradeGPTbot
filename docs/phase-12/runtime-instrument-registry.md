The PostgreSQL implementation is the production backend undergoing native acceptance; unit and packaging stores are explicit fixtures.

Each accepted replacement commits the current head, immutable full record revision and independent rules/metadata anti-reuse identities in one transaction. Opaque native IDs are not lexicographically ordered. A positive PostgreSQL BIGINT logical revision advances once per accepted replacement and is transported as a lossless integer string. Exact current semantic replay returns the existing revision without another write effect. Independent A→B→A metadata or rule reuse rejects, including after restart. Effective-time regression and equal-version content conflicts reject.

Revision predecessor foreign keys prove a contiguous durable chain. Each immutable revision references both version identities; each version's origin references its immutable revision. Deferred origin constraints resolve the atomic insertion cycle at COMMIT. History cannot be removed to reclaim capacity: UPDATE, DELETE and TRUNCATE guards and foreign keys preserve the record/version chain. SQL read/publication checks require matching current immutable evidence. A trusted DDL owner can alter constraints or replace a database; backup/restore must preserve the entire authority schema, and is not a supported history reset mechanism.

Publication serializes one exact exchange/region/market/environment scope with an advisory transaction lock before sorted instrument rows. This protects absent-row, symbol ownership and competing writer races. A batch contains at most 300 distinct instruments / 1 MiB and a record at most 32 KiB; a failed member rolls back the whole batch. There is no elapsed-runtime version budget. Permanent history uses database storage; provision disk/backup capacity and monitor its growth. Finite current cache size and connection admission bounds are independent of history length.

## Reads and freshness

The existing synchronous get remains an **observational projection**, not a linearizable or financial authority read. At most 300 configured current records are retained; historic identities are never copied into a process Set. One bounded recovery read runs at a time every 250 ms. The projection lease expires 1000 ms after monotonic read-start time, so a delayed response cannot rejuvenate it. Recovery failure, missing previously recovered rows, equal-revision conflict, close or expired lease denies reads. Original metadata validity/status/expiry checks remain required.

readCurrent performs an authoritative PostgreSQL read in its own bounded transaction and updates the projection. Exchange Core invokes it before request admission and repeats it after asynchronous mutation authorization, followed by its current scope/rules/capability/deadline guards. Every parsed stream event rechecks the captured metadata/rule identity and current registry availability. Metadata replacement, expiry or unavailable projection requires resync. Streams do not perform a database round trip for each tick.

The one-second projection bound is not a Risk certificate and does not remove a concurrent-write race by itself. Certified atomic PLACE approval and its final dispatch gate read and lock the same durable registry rows with the other current sources in their own authority transaction; separate readCurrent transactions do not certify that source vector. Certified CANCEL/AMEND integration remains required. Old reference get/put callers remain synchronous; writable put may now return a Promise, and all four metadata transports await known durable commit with the actual request signal/deadline. Production batch publication is atomic; the fallback exists only for explicit reference/contract fixtures.

Additive migration 202610080007_bounded_registry_recovery addresses a confirmed recovery deadline regression as history grows. A single sorted current-record cursor performs complete-primary-key checks of immutable revision, rules identity and metadata identity. Both PostgreSQL custom/generic plans must complete within the existing one-second physical budget (900ms SQL component test). History is never deleted or reused. Output is a bounded array; missing/inconsistent history still rejects recovery. No deadline or runtime privilege is relaxed.

## Physical lifecycle and SQL role

The backend owns each physical TCP Socket before PostgreSQL connect/authentication starts. At most four operations are admitted; there is no unbounded pool wait queue. Abort/deadline destroys that socket, observes the actual Client promise settlement and prevents late cache publication. Transactions cap at three seconds, connection setup at one second, and statement/query/idle-transaction timeouts provide additional bounds. The accepted Linux PostgreSQL server profile uses client_connection_check_interval=100ms to detect socket loss while a statement waits; native tests must prove backend disappearance. COMMIT acknowledgement loss returns failure without claiming commitment; recovery and exact current replay resolve the durable state without a second version effect. Native server-side lock cancellation and physical client teardown require acceptance evidence, not only a Promise.race.

The NOLOGIN ctp_instrument_registry group has only schema USAGE and EXECUTE on publish(jsonb,jsonb) / read_current(jsonb,jsonb). All helper functions explicitly revoke PUBLIC EXECUTE; all three tables ENABLE/FORCE RLS and expose no direct runtime grants. SECURITY DEFINER functions use search_path=pg_catalog. Startup rejects elevated flags/group flags, extra/transitive memberships, table/column grants, schema ownership/CREATE, database TEMP/CREATE and execution of any extra function in authority schemas. SQL validates scope, canonical decimal units, constraints, contract assets, identity freshness and known fields independently of TypeScript. Deployment verifies the migration owner without BYPASSRLS.
