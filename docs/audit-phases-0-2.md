## Обнаруженные проблемы

Приоритет P1 означает нарушение основного принятого инварианта, которое нужно закрыть до использования будущими финансовыми сервисами; P2 — несогласованность контракта или проверки. Сейчас API предоставляет только health endpoints: ни одна находка не означает выполненную торговую операцию или подтверждённую утечку пользовательских данных.

**A08, P2 — зависимость offline deploy от ранее прогретого policy cache.** Свежая Docker-сборка прошла frozen install и build, но остановилась на `ERR_PNPM_NO_OFFLINE_META` для `zod`. В pnpm 11 online-проверка release age может использовать attestation без полной registry metadata; производный deployment lockfile требует самостоятельной проверки. Добавлена online-подготовка `deploy --prod --lockfile-only` с исходными правилами. Итоговый deploy остаётся offline, в Docker также с `RUN --network=none`, и проверяется побайтовое равенство обоих lockfile. Тот же порядок применён к clean runner для API и БД. Ни версии, ни опубликованные миграции, ни supply-chain ограничения не ослаблены. Подробности и источник: [deployment](deployment.md).

**A09, P2 — тест рестарта PostgreSQL терял данные.** `tmpfs` для PGDATA удалял кластер при stop/start, поэтому проверка восстановления фактически включала повторный `initdb`. Диагностическая проба `test-results/audit-tmpfs-restart.json` подтвердила исчезновение контрольной таблицы; локальное подключение восстановилось за 1486 мс. PGDATA переведён на `postgres-data` volume с областью уникального Compose project; runner удаляет его через `down --volumes`. Существующие три service-теста теперь проверяют сохранение записи, а runner сохраняет ограниченную диагностику отказа с удалением секретов. Бюджет восстановления 6500 мс сохранён; повторные локальные проверки прошли.

В [первом CI исправлений](https://github.com/dendenden-boop/tradeGPTbot/actions/runs/34750802426), commit `f186b9a`, jobs Linux и Windows прошли, но service job получил отказ восстановления PostgreSQL за 6500 мс. Следующая проверка Redis также завершилась при `postgres: down`, то есть отказ был каскадным. Потеря данных в fixture доказана отдельно; без PostgreSQL-логов этого CI она не объявляется подтверждённой причиной его длительного отказа. Повторный CI после A09 прошёл; исходный отказ сохранён в истории проверок.

Повтор после A09 подтвердил сохранение данных и 91 DB-тест, затем выявил отдельный timeout административного DROP DATABASE: PostgreSQL ожидал дискового checkpoint. Обычные SQL-проверки и runtime-дедлайны не менялись, повтор timed-out DROP и отключение fsync не применяются. Финальный локальный прогон прошёл полностью; DROP+CREATE заняли 7142 мс, все fresh/upgrade/repeat/reset gates PASS (`audit-0-2-integration-storage-final.log`, `database.json`). Маскирование диагностик учитывает также случайные 48-hex пароли дочерних DB-ролей; шесть unit-тестов проверяют SQL, DSN, JSON, границы значения и сохранение digest/UUID.

Первый расширенный PostgreSQL-прогон после исправления ошибки fixture: **75 тестов, 53 PASS и 22 ожидаемых FAIL**. Все 22 отказа возникли потому, что запрещённая операция успешно выполнилась: 5 несовместимых ссылок, 16 изменений durable evidence и 1 ввод binary float. Исходные 47 PostgreSQL-тестов продолжили проходить. JSON и лог этого воспроизведения сохранены в ignored `test-results/audit-0-2-regressions-before.*`.

## Дополнительная проверка самих исправлений

Рецензирование новой миграции выявило риск блокировки AMEND: его собственный intent и reservation нельзя приравнивать к исходному PLACE intent ордера. Поэтому attempt получает самостоятельную связь с command intent и целевым order; AMEND/CANCEL имеют явный `OrderIntent.targetOrderId`. Положительные сценарии отдельного AMEND и CANCEL с отсутствующим reservation дополняют отрицательные проверки scope/operation/hash. Старые неоднозначные AMEND/CANCEL без сохранённой команды/target блокируют upgrade; миграция не придумывает для них evidence.

Отдельно выполнен upgrade под владельцем таблиц без superuser/BYPASSRLS: новая миграция выполняет backfill с транзакционной блокировкой необходимых таблиц и временным снятием FORCE только для владельца, затем восстанавливает FORCE перед commit. Обычные runtime роли продолжают подчиняться RLS. Проверки восстановленных ограничений после успешного и неуспешного upgrade прошли.

Уточнена семантика Order: durable identity и однажды присвоенный exchange ID неизменяемы, а текущие quantity/price могут обновляться будущим amendment/reconciliation writer. Исходная команда остаётся в неизменяемом Intent/Attempt. Для нового Decimal guard проверены также Linux entrypoint генератора и ограничение обхода вложенных/циклических массивов.

## Граница следующего этапа
